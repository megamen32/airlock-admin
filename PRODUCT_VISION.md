# Product Vision — Airlock × GPTAdmin × ExManager

> Документ-черновик продукта. Не план релизов (тот в `ROADMAP.md`) и не
> операционный ранбук (тот в `AIRLOCK_ADMIN.md`). Здесь — что мы строим
> и зачем.

---

## В одной строке

**Самохостедный корпоративный AI-секретарь для каждого сотрудника и
единая панель управления бизнесом для руководителя — на AGPL-стеке.**

Большие компании покупают это за $20–80/мес за рабочее место у Microsoft
Copilot или Notion AI. Мы делаем то же самое, но:
1. **Своё железо** — данные клиента никуда не утекают (никаких «улучшающих
   моделей на ваших документах»).
2. **Реальные действия** — не «перескажу письмо», а «создам задачу,
   отвечу в Slack, соберу презентацию, отправлю в почту».
3. **Полный контроль** — IT видит каждое действие каждого агента, может
   отозвать одним кликом.

## Три слоя, одна экосистема

```
┌──────────────────────────────────────────────────────────────────────┐
│                       ExManager (front)                              │
│   desktop / mobile / web  ·  единый чат-интерфейс сотрудника         │
│   «спроси свои файлы, собери презу, открой почту, напиши отчёт»     │
└──────────────────────────────────────────────────────────────────────┘
            │                                       │
            │ delegated actions                     │ read-only context
            ▼                                       ▼
┌─────────────────────────────────┐    ┌────────────────────────────┐
│           Airlock (cloud)       │◀──▶│  GPTAdmin (edge, per device)│
│  Identity · Grants · Audit      │    │  реальные руки на машине    │
│  Agent runtime · App store      │    │  shell · file · MCP · UI    │
│  Approval workflow · Billing    │    │  approval-gated, peer-aware │
└─────────────────────────────────┘    └────────────────────────────┘
            │                                       │
            └───────────────┬───────────────────────┘
                            ▼
                единый audit log + policy engine
                (кто, что, когда, на какой машине, с какими правами)
```

**Ключевая идея:** Airlock решает «можно ли» и «кто такой». GPTAdmin
делает «как именно на этой машине». ExManager — это лицо, через которое
сотрудник общается со всем этим. Разделение полномочий = каждый слой
делает одну вещь хорошо и может быть заменён независимо.

## Четыре персоны, четыре сценария

### 1. Сотрудник (Аня, маркетолог)

- Утром открывает Telegram с личным ассистентом (бывший ExManager),
  видит: «3 непрочитанных от Иванова, совещание в 11 перенесено,
  вчерашняя презентация не дослана Васе».
- Просит: «ответь Иванову что я пришлю сегодня к 14, перенеси совещание
  на 12 и собери презу по новой акции из этих трёх PDF». Агент
  справляется сам, показывает что сделал, просит approval на отправку
  письма.
- Вечером с телефона (Telegram или PWA `/app`): «что у меня с отчётом
  за неделю?» — ExManager собирает из Gmail + Apple Calendar +
  локальных файлов, присылает черновик, Аня правит голосом.

**Что для этого нужно:** ExManager с доступом к рабочим приложениям
(CRM/почта/календарь/docs), airlock-агент с grants на эти коннекторы,
GPTAdmin на её ноуте для локальных действий (Finder, браузер, скриншоты).

### 2. Руководитель (Петр, CTO)

- Открывает дашборд в Airlock: «кто из команды сегодня работает с
  AI», «какие действия были заблокированы approval-ом», «сколько токенов
  ушло на отдел», «какие интеграции просят сотрудники».
- Видит: «Аня попросила доступ к CRM-продакшн — это норма для её
  роли?». Одной кнопкой даёт grant с лимитом на 30 дней.
- Раз в неделю — отчёт «AI-эффективность отдела»: какие задачи
  автоматизированы, где люди тратят время, что нужно дообучить.

**Что для этого нужно:** агрегатор телеметрии по всем агентам, RBAC с
ролями уровня отдела, метрики по токенам/стоимости, политика «запросил
доступ → одобри/откажи с правилом по умолчанию».

### 3. IT-админ (Саша, SecOps)

- Видит все машины с GPTAdmin в реальном времени: кто подключён,
  версии, состояние mesh, аномалии.
- В один клик отзывает у бывшего сотрудника все токены на всех
  машинах, видит audit-trail последних действий.
- Политики уровня компании: «все агенты с доступом к prod-базам
  требуют 2-step approval», «машины вне MDM-зоны — read-only режим».

**Что для этого нужно:** fleet-вью в airlock, mesh-discovery хабов,
центральный kill-switch, политики на уровне grants, интеграция с
MDM/IdP компании (Okta/AzureAD/Keycloak).

### 4. Владелец бизнеса (сам)

- Один экран: «AI сделал за компанию Х действий, сэкономило Y часов,
  стоило Z рублей, лимиты/бюджеты под контролем».
- Approval-очередь для high-risk действий, delegated admin для
  рутины, audit-export в любую удобную систему.

## Технические пробелы до продукта

Перечисляю в порядке приоритета. Для каждого — какой кусок закрывает.

### Tier 1 — неделя работы, без этого стенд не продукт

1. **«Гладкая» установка GPTAdmin.** Сейчас: ручной systemd + JSON в
   `/etc/gptadmin`. Нужно: signed installer (`.deb/.pkg/.msi`), post-install
   `gptadmin enroll <airlock-url> <tenant-token>` → авторегистрация
   в airlock, автообновление через airlock-rollout. Без этого никто
   кроме нас агентов не поставит.

2. **Desktop-tray для GPTAdmin.** Иконка в трее с состоянием (online/
   pending approval / error), кнопка «приостановить AI на этой машине»
   для приватности, журнал последних 20 действий. Сейчас вся
   observability — через `gptadmin status` в CLI.

3. **Airlock Fleet-страница.** Карта машин с GPTAdmin: какие онлайн,
   какие отстали по версии, какие запрашивали approval, последние
   ошибки. Должна жить внутри существующего airlock admin UI
   (отдельный route `/admin/fleet`), не быть отдельным SPA.

4. **Готовые grant-шаблоны по ролям.** Сейчас grant создаётся руками.
   Нужно: «сотрудник», «тимлид», «финансист», «CEO», «контрактор» —
   каждый с дефолтным набором permissions, политикой approval и
   лимитом токенов.

### Tier 2 — пара недель, превращает demo в пилот

5. **ExManager как переиспользуемый шаблон агента.** Не отдельный
   продукт, а «personal-secretary» skill, который ставится в airlock
   одной командой и конфигурируется под tenant (список коннекторов,
   токены на почту/календарь, имя/аватар).

6. **Коннекторы к рабочим сервисам из коробки.** Gmail (через userio
   MCP — уже работает, остаётся упаковать как шаблон), Google Calendar
   (CalDAV/OAuth), Apple Calendar (CalDAV через clouddav). Slack, Jira,
   Notion, Bitrix24 — **вне MVP** (никто в команде не использует).
   Confluence, GitHub — позже по запросу.

7. **Approval-flow в мобильном приложении.** Push-уведомление
   «Агент Ани хочет отправить письмо клиенту Х на сумму Y. Разрешить?»
   с кнопками «да/нет/изменить». Сейчас approval только в web UI
   airlock.

8. **Audit-log с тегами и поиском.** Сейчас всё в Postgres airlock,
   фильтры базовые. Нужно: полнотекстовый поиск, теги («pii»,
   «finance», «prod-access»), экспорт в SIEM (Splunk/Elastic).

### Tier 3 — месяцы, превращает пилот в платформу

9. **Мультитенантность в одном инстансе.** Один airlock = много компаний
   с полной изоляцией. Сейчас это «один владелец». Нужна модель
   tenant → users/agents/connectors, миграция схемы.

10. **Биллинг и квоты.** Метрики по тенанту (токены, actions, storage,
    seats), paywall в free/community/team/business tiers. AGPL-self-hosted
    остаётся бесплатным, коммерческие фичи (SSO/SIEM/multi-tenant UI)
    — за деньги (как у airlock сейчас).

11. **Маркетплейс агентов.** Каталог шаблонов агентов («PR-reviewer»,
    «Standup-drafter», «Code-archaeologist», «Customer-onboarding»),
    каждый с README, IAM-профилем и ценой. Установка одной кнопкой.

12. **Skills/плагины от сообщества.** AGPL разрешает форки и продажу
    агентов как отдельный продукт поверх нашей платформы. Нужен
    открытый формат манифеста (`agent.yaml`) и реестр совместимости.

## MVP — что показать через 4 недели

**Целевой сегмент:** стартапы. Self-hosted/on-prem, своя железка или
VPS, без SaaS-зависимостей.

**Сценарий-кандидат:** «офис из 5 человек ставит систему за час, через
месяц экономит 10 часов в неделю».

- 1 машина-сервер (airlock + OmniRoute) на VPS/своём железе
- 5 ноутбуков сотрудников с GPTAdmin (через готовый installer)
- 5 аккаунтов в airlock, шаблонные grants
- 3 коннектора из коробки: **Gmail** (через userio MCP, уже есть),
  **Google Calendar**, **Apple Calendar**
- ExManager-агент у каждого сотрудника (живёт в Telegram + имеет
  `/app` PWA-вебморду), умеет: «собери презу», «сводка за день»,
  «ответь на письмо в моём стиле»
- Fleet-страница у руководителя
- Audit-log с экспортом в CSV

**Из MVP выпилено:** Slack, Jira, Notion, Bitrix24, CRM, MDM, мобильное
нативное приложение (Telegram + PWA хватает).

**Out of scope для MVP:** мультитенантность, мобильное приложение,
маркетплейс, биллинг, интеграции с CRM/BI, MDM.

Этот MVP — продаваемый пилот: 1–3 компании-партнёра внедряют, мы
получаем фидбек и case studies.

## Бизнес-модель (варианты, не выбран)

| Модель | Плюсы | Минусы |
|--------|-------|--------|
| **Только self-host AGPL** | Максимальная простота, нет инфра-расходов, маркетинг через GitHub | Нет дохода, только лицензия на чужой код |
| **Self-host + коммерческие дополнения** | Как airlock: SSO/SIEM/multi-tenant UI за подписку, base — бесплатно | Нужен отдел продаж, защита от копирования |
| **Managed-хостинг (SaaS)** | Повторяемый доход, easy onboarding, быстрый рост | Несёт риски хранения чужих данных, нужно 24/7 ops |
| **Белый лейбл для интеграторов** | Партнёры продают, мы лицензируем | Долгий цикл сделки, нужны сертификации |
| **Гибрид: self-host + managed для SMB** | AGPL для крупных/параноиков, SaaS для остальных | Двойная кодовая база риск |

Самый реалистичный путь: стартуем с «self-host + коммерческие
дополнения» (как делает airlock сейчас), параллельно строим managed
для SMB — это основной источник дохода на горизонте года.

## Именование и позиционирование

Внутреннее кодовое имя пока пусть будет **«Триада»** (или
любое другое, это вопрос брендинга). Что важно:

- **Airlock** остаётся Airlock — это признанный проект, своя аудитория,
  своя репа, свой сайт (`airlock.run`). Не ломаем.
- **GPTAdmin** остаётся GPTAdmin — тоже бренд, тоже AGPL-сообщество.
- **ExManager** — название «секретаря». Если делаем его шаблоном
  агента в airlock, он может называться `Personal Secretary` или
  `Companion` — нейтральнее и переиспользуемо.
- **Продукт целиком** нуждается в имени. Варианты (все требуют проверки
  домена и товарного знака): см. «Метод для выбора имени» ниже.
  Свежая пачка идей — в финальном сообщении сессии.

## Что я бы НЕ делал сейчас

- Не делать мобильное приложение — Telegram + PWA `/app` достаточно
  для v0.
- Не строить биллинг до первого платящего пилота.
- Не открывать маркетплейс до понимания, какие агенты реально нужны
  (определится из MVP).
- Не рекламировать «AI-секретаря» без UX-тестов на 5 людях — слова
  «AI» сейчас вызывают отторжение у половины рынка.

## Метод для выбора имени

Имя должно:
- работать в трёх рынках (СНГ / EU / US), не ассоциироваться с конкретным
  вендором и не быть занятым в `.app` / `.so` / `.work` / `.team` / `.run`;
- нести идею «своё рабочее место + контроль руководителя»;
- не быть трендовым AI-словом (никаких `ai`, `agent`, `flow` в имени —
  это выгорает за год).

Короткий чек перед фиксацией:
1. Проверить домен в зонах `.app` / `.so` / `.work` / `.team` / `.run`.
2. Поиск в GitHub и npm — нет ли уже проекта с таким именем и 1k+ звёзд.
3. Поиск в USPTO/EUIPO/RU ROSPATENT — нет ли живого товарного знака.
4. Произнести вслух носителю английского и русского — не ломается ли.
