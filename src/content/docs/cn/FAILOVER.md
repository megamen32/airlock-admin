# 故障转移和降级恢复

GPTAdmin 的设计目标是，即使一台机器宕机，控制平面也不会随之瘫痪。一个备用节点可以通过相同的公网隧道路径保持待命中心的可达性，从而使服务在降级模式下持续运行，足够时间来检查日志、联系存活的服务器并修复主节点。

这并非神奇的多主复制。当主节点宕机时，一些实时的内存状态可能会陈旧或暂时不可用。重要的是，GPTAdmin 将操作轨迹存储在磁盘上：排队/后台任务、大型 stdout/stderr 溢出文件、shellmcp 暂存文件、出件箱响应、注册表快照、故障转移运行时状态和服务日志。这意味着系统可能会损失一点即时性，但恢复工作不是盲目的，而且大多数任务证据不会永远丢失。

## 角色

| 角色 | 功能描述 |
|------|--------------|
| **主中心** | 正常的活动 GPTAdmin 中心、管理 UI、MCP 中继、Action/OpenAPI 端点、队列和路由。 |
| **备用节点** | 运行待命中心或本地代理，监控公网健康 URL，并在主节点停止响应时提升自身。 |
| **隧道** | 公网入口。在发生事件时，它会被重定向到备用节点，因此客户端仍然拥有一个 HTTPS 入口点。 |
| **恢复路径** | 当主节点恢复时，它会向活动的备用节点发送一个签名的恢复/降级请求，使备用节点重新成为客户端/待命模式。 |

## 主节点宕机时会发生什么

1. 备用看门狗会按间隔检查主节点的公网健康端点。
2. 超过配置的故障阈值后，备用节点确认公网 URL 仍然不健康。
3. 备用节点通过启动其本地中心/代理和隧道客户端来提升自身。
4. 现有的 AI 客户端和管理员仍然可以通过公网 URL 访问 GPTAdmin，但系统处于降级模式。
5. 存活的 shell/MCP 服务器会重新连接或继续轮询。宕机的服务器显示为离线/陈旧，并可以从备用控制平面进行修复。
6. 当主节点再次健康时，主节点会发送一个签名的恢复消息。活动的备用节点降级并返回待命/客户端模式。

## 降级模式下仍然正常工作的功能

- 备用节点上的管理 UI 和健康端点。
- 针对仍可从备用节点到达或已通过长轮询连接的服务器的 shell/MCP 操作。
- 读取已持久化到处理这些任务的节点磁盘上的排队/后台任务状态。
- 通过暂存文件而不是在聊天上下文中丢失大型命令输出。
- 当传输重新连接时，基于出件箱的排队响应交付。
- 事件分类：日志、服务状态、隧道状态和恢复命令。

## 可能暂时陈旧或丢失的内容

- 非常近期的内存计数器、活动请求列表或尚未持久化或同步的最后看到的数据。
- 在故障发生的确切时刻正在运行的机器上的任务。其最后持久化的暂存/日志状态仍然有用，但进程本身可能需要重新运行。
- 只存在于宕机服务器上的本地资源。
- 托管在宕机服务器上的 MCP 工具，直到该服务器恢复或另一个节点托管了相同的工具。

GPTAdmin 将此视为优雅降级：首先保持较小的控制平面存活，然后利用它来恢复更大的控制平面。

## 操作员检查清单

在活动节点上：

```bash
gptadmin urls
systemctl status gptadmin-hub gptadmin-tunnel-frpc --no-pager
journalctl -u gptadmin-hub -n 120 --no-pager
```

在备用节点上，检查看门狗/代理运行时：

```bash
ps aux | grep -E 'gptadmin|failover|frpc' | grep -v grep
curl -fsS http://127.0.0.1:9001/healthz
curl -fsS http://127.0.0.1:9101/healthz
```

然后，在删除或激进重启之前检查持久化状态：

```bash
find /var/lib/gptadmin -maxdepth 4 -type f | sort | tail -100
find /data/gptadmin-failover -maxdepth 4 -type f | sort | tail -100
```

查找暂存、出件箱、运行时和日志文件。它们是恢复的轨迹。

## 当前 HAOS 布局

一个紧凑的备用节点可以运行一个类似这样的循环：

```text
/data/gptadmin-failover/loop.sh
/data/gptadmin-failover/gptadmin-failover-proxy.py --listen 127.0.0.1:9101 --upstream http://127.0.0.1:9001
/data/gptadmin-failover/runtime.json
/data/gptadmin-failover/failover_state.json
/data/gptadmin-failover/logs/watchdog.log
```

确切的路径取决于部署，但逻辑是相同的：看门狗检查主节点，只有在达到阈值/确认后才提升备用节点，保留磁盘状态，并在主节点返回时接受签名的恢复请求。

## 设计原则

宁愿“存活且降级”，也不愿“完美但宕机”。在停机期间，GPTAdmin 应该保持足够多的部分可达，以便回答：什么存活了，什么宕机了，哪些任务正在运行，日志在哪里，以及如何恢复主节点。
